# Free managed stack for the workout PWA

Research date: 2026-07-23. Sources are first-party product documentation and pricing pages.

## Recommendation

Use a small hybrid:

- **Supabase Free** for Postgres, Authentication, Row Level Security, the Data API, and one narrowly scoped Edge Function for the private Custom GPT Action.
- **Cloudflare Pages or Workers Static Assets Free** for the compiled PWA. Static asset requests are free and unlimited; only requests that execute Worker code consume the Workers quota ([Cloudflare static-assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)).
- **IndexedDB in the PWA** as the local source of truth during an Active Workout, with an explicit outbox/sync layer. Supabase does not provide Firestore-style browser offline synchronization, so this is application work, not a switch in the Supabase SDK.

This is the best fit because Workouts, Exercise Blocks, Exercises, Sets, Planned Workouts, recurrence, Personal Records, and Fitbod imports form a relational model. Supabase provides a real Postgres database and standard import/dump paths ([Supabase database overview](https://supabase.com/docs/guides/database/overview)), while database-enforced RLS can isolate every Member's rows ([Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)). Firebase has the easiest offline client, but Firestore is a schemaless document database rather than tables and rows ([Firestore data model](https://firebase.google.com/docs/firestore/data-model)); progress queries and migrations would require more denormalization and vendor-specific design. Cloudflare D1 is relational and has excellent free limits, but Cloudflare does not offer an end-user auth/data-isolation combination as direct as Supabase Auth plus Postgres RLS.

The recommendation is genuinely $0 within the stated quotas and does not need a paid OpenAI API: the Administrator's Custom GPT calls the app's Action endpoint. The unavoidable privacy boundary is that any history returned by that endpoint is sent to ChatGPT for the requested recommendation; the endpoint should therefore return only the minimum fields needed.

## Required implementation boundaries

1. Bootstrap the Administrator account, then disable public signup. Persist the Supabase browser session. Supabase sessions last indefinitely by default; short-lived access tokens are silently renewed with single-use refresh tokens that do not expire unless the session is terminated by sign-out or a security-sensitive action ([Supabase sessions](https://supabase.com/docs/guides/auth/sessions)). Browser storage can still be cleared by iOS or the person using the device, so no web stack can promise an absolutely permanent login.
2. Put a non-null `member_id` on every Member-owned row and enable RLS on every exposed table. Use `auth.uid() = member_id` policies for select, insert, update, and delete. Administration/invitations must not bypass fitness-data policies.
3. Keep the PWA shell public. Public source code and public static files do not expose data when secrets remain server-side and RLS is correct. Do not put a Supabase secret/service key in the PWA or GitHub; only the publishable browser key belongs there.
4. Make the Edge Function a narrow GPT adapter. Authenticate it with a dedicated secret, bind it server-side to the Administrator's fixed Member ID, expose read-only recommendation context, and permit writes only to draft Workout Recommendations. Never accept an arbitrary Member ID from the GPT and never expose the service-role credential. Supabase documents both user-JWT and named-secret modes for Edge Functions ([securing Edge Functions](https://supabase.com/docs/guides/functions/auth)).
5. Back up independently. Supabase Free does not include user-accessible automatic backups; Supabase recommends regular `supabase db dump` exports for free projects ([Supabase backups](https://supabase.com/docs/guides/platform/backups)). Add a manual encrypted backup procedure before the private beta and automate it later if a safe free runner is available.

| Structured workout data | Full Postgres with foreign keys, SQL aggregation, migrations, and portable dumps. Best semantic fit. | Firestore is NoSQL documents/collections. Firebase SQL Connect is not a lasting free alternative: Spark gets a 90-day trial, after which the database is archived and later deleted unless upgraded ([SQL Connect pricing](https://firebase.google.com/docs/sql-connect/pricing)). | D1 is managed SQLite-style SQL and supports indexes and foreign keys ([D1 query guidance](https://developers.cloudflare.com/d1/best-practices/query-d1/)). Good fit, though less portable/capable than Postgres for future analytics. |
| Auth and persistent sign-in | Built-in. Sessions are indefinite by default with automatic refresh. Excellent fit. | Built-in. Web `LOCAL` persistence is indefinite until explicit sign-out and is the browser default ([Firebase auth persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence)). Excellent fit. | Access is free for up to 50 users ([Cloudflare Zero Trust pricing](https://www.cloudflare.com/plans/zero-trust-services/)), but its global/application/policy sessions have a maximum of one month ([Access session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)). A custom auth system could avoid that, but adds security-sensitive code. |
| Member isolation | Native Postgres RLS, evaluated at the database for every client request. Strongest and simplest option. | Firestore Security Rules can require `request.auth` and compare ownership fields ([Firestore rule conditions](https://firebase.google.com/docs/firestore/security/rules-conditions)). Strong when every query and rule is designed together. | D1 has no Supabase-style per-request database RLS. A Worker must authenticate and add ownership checks to every query. Cloudflare Access protects the front door but does not replace row-level authorization. |
| Offline-first workout logging | No built-in browser sync. Use IndexedDB, durable local writes, idempotent mutation IDs, and an outbox. More work, but gives explicit conflict rules. | Best built-in option: Firestore caches reads and writes locally and synchronizes on reconnect; web support includes Chrome and Safari. Conflicts to the same document are last-write-wins ([Firestore offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline)). | No built-in D1 browser sync. Use the same IndexedDB/outbox approach as Supabase. |
| Static PWA hosting | Not a frontend host; pair with Cloudflare Pages/Static Assets. | Firebase Hosting includes 10 GB stored and 10 GB/month transfer on Spark; it disables the site after a grace period if the transfer limit is exceeded ([Firebase Hosting quotas](https://firebase.google.com/docs/hosting/usage-quotas-pricing)). | Strongest hosting offer: static requests are unlimited and free; Pages Free allows 500 builds/month and 20,000 files ([Pages limits](https://developers.cloudflare.com/pages/platform/limits/)). |

Free includes 500,000 invocations ([Edge Function usage](https://supabase.com/docs/guides/platform/manage-your-usage/edge-function-invocations)). Keeps auth, data, and Action logic in one backend. | Cloud Functions require Blaze to deploy, even though Blaze includes a no-cost allowance ([Functions deployment](https://firebase.google.com/docs/functions/get-started)). Staying card-free therefore needs a Cloudflare Worker as a second backend. | Natural fit: a Worker can expose the Action and query D1. Free allows 100,000 dynamic requests/day and 10 ms CPU per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Protect with a service token/API key and enforce the one-Administrator scope in code. |
| Core free quota | 2 active projects, 500 MB database, 50,000 MAU, 5 GB egress, 1 GB object storage, and 500,000 Edge Function calls ([Supabase pricing](https://supabase.com/pricing)). Far beyond a tiny workout app, except media should remain modest. | One free Firestore database: 1 GiB stored, 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day, and 10 GiB/month egress ([Firestore pricing](https://firebase.google.com/docs/firestore/pricing)). | D1: 5 GB total, 5 million rows read/day, 100,000 rows written/day, with no D1 egress charge; Workers: 100,000 requests/day ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). |
| Inactivity | Material caveat: Free projects with low activity are paused after about seven days; even some light use may be insufficient. A few database requests per day are normally enough ([Supabase pausing](https://supabase.com/docs/guides/platform/free-project-pausing)). Do not build artificial keep-alive traffic; accept a possible restore after a long break and keep offline logging functional. | No inactivity pause is documented for Spark; quotas shut off affected products after limits are exceeded until reset ([Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)). | No inactivity pause is documented; free usage is enforced through daily/monthly quotas. |
| Credit card and overage risk | Free is $0 and cannot incur overage charges; excess use is restricted rather than billed ([Supabase cost control](https://supabase.com/docs/guides/platform/cost-control)). A payment method is needed only when moving to paid billing. | Spark explicitly needs no payment information. Blaze requires a billing account/payment method, and costs cannot be hard-capped ([Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans), [Firebase FAQ](https://firebase.google.com/support/faq)). | Cloudflare advertises starting free with no credit card; Free fails requests above limits rather than silently upgrading ([Cloudflare products](https://www.cloudflare.com/products/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). |
| Backup/export | Standard Postgres reduces lock-in. Free needs scheduled/manual `db dump`; paid Pro starts at $25/month and includes seven days of daily backups ([Supabase pricing](https://supabase.com/pricing)). | Managed Firestore export/import requires billing/Blaze and produces a service-specific LevelDB format ([Firestore export/import](https://firebase.google.com/docs/firestore/manage-data/export-import)). Application-level JSON export is advisable. | D1 includes always-on Time Travel for seven days on Free ([D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)) and `wrangler d1 export` produces SQL ([D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/)). Best free recovery story of the three. |
| Upgrade and lock-in | Clear but relatively large first step: Pro starts at $25/month. Postgres schema/data and Edge Functions' Deno/TypeScript are portable. Auth migration still takes work. | Blaze is pay-as-you-go and Functions unlock only after linking billing. Firestore client/data modeling and proprietary exports create the highest data-layer lock-in. | Workers Paid starts at $5/month; D1 exports SQL. Worker APIs and D1 bindings still create platform coupling, and replacing custom/Access auth is application work. |

## Decision caveats

- **Supabase pausing is the one serious compromise.** For a regularly used workout app it may never occur, but a private beta can be quiet. Offline-first behavior must not depend on the project being awake. If pauses prove annoying during the one-month trial, reconsider Firebase + Cloudflare Worker before paying, rather than adding artificial traffic.
- **Firebase is the fallback if effortless offline sync dominates relational clarity.** Its auth, hosting, and Firestore remain card-free on Spark, but the Custom GPT Action still needs Cloudflare Workers and backups need an application-level export.
- **All-Cloudflare is the fallback if zero pausing and free recovery dominate.** It is operationally attractive, but choosing it means owning authentication/session design or accepting Access reauthentication at least monthly, plus enforcing every Member boundary in Worker code.
- **Exercise illustrations can consume storage/transfer quickly.** Prefer a separately licensed external catalog or small optimized static assets; do not commit to Supabase Storage until licensing and offline-cache size are understood.
- **Free tiers are policies, not guarantees.** Recheck the linked pricing pages immediately before deployment and record the chosen region, quotas, and a migration plan in an ADR.
